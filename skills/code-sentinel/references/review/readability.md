# `readability` — 복잡도 및 가독성

이 영역을 검토할 때 읽습니다. 공통 원칙은 `principles.md`, 심각도·확신도 정의와 보고 규칙은 `severity.md`를 따릅니다. 각 영역 문서는 다른 영역 문서 없이 쓸 수 있게 독립적으로 작성했습니다.

## 확인 항목

- **과도한 추상화:** 구현이 하나뿐인 인터페이스·팩토리, 간접 계층이 늘어 흐름을 따라가기 어려움
- **복잡한 분기:** 깊은 중첩, 긴 함수, 플래그 인자로 동작이 갈리는 함수, 부울 조건의 과도한 조합
- **중복 코드:** 같은 변경 안에서 복사한 블록(한쪽만 고쳐질 위험)
- **주석과 구현의 불일치:** 주석·docstring·README가 바뀐 동작을 반영하지 않음
- **오해를 부르는 이름:** 이름과 실제 동작이 다름(`isValid`가 부수 효과를 냄). 실제 버그로 이어지면 `correctness`로 보고
- **매직 넘버·문자열**, 맥락 없는 TODO·FIXME

## 판단 기준

- balanced에서는 이해·유지보수에 구체적인 비용이 있을 때만 보고합니다(예: 같은 로직 3곳 복사로 한 곳만 고쳐질 위험).
- strict에서는 개선 제안 수준도 보고하되 심각도는 대부분 Low입니다.

## 심각도 예시

판단 기준을 맞추기 위한 예시입니다. 실제 심각도는 `severity.md` 1.1절의 요소로 조정합니다.

| 심각도 | 예시 |
|---|---|
| Critical | (해당 사례 거의 없음) 주석과 실제 동작이 정반대라 운영자가 주석대로 설정하면 데이터가 삭제되는 경우 → 실제 피해 기준으로 `ops`·`correctness`로 보고 |
| Critical | (해당 사례 거의 없음) 잘못된 이름 때문에 실제 오호출이 이미 생김 → `correctness`로 보고 |
| High | 같은 검증 로직을 세 곳에 복사했고 이번 변경에서 한 곳만 고쳐 나머지 두 경로가 이전 규칙을 따름 (불일치가 기능 문제면 `correctness`) |
| High | 함수 이름 `isAllowed`가 권한 확인 외에 상태를 바꿔 호출자가 오해할 위험이 큼 |
| Medium | 5단계 이상 중첩된 분기와 플래그 인자로 새 조건 추가 시 누락 위험 |
| Medium | docstring이 바뀐 반환 형식을 반영하지 않음 |
| Low | 의미를 알 수 없는 매직 넘버 |
| Low | 구현이 하나뿐인 인터페이스와 팩토리 추가 |
