# `performance` — 성능

이 영역을 검토할 때 읽습니다. 공통 원칙은 `principles.md`, 심각도·확신도 정의와 보고 규칙은 `severity.md`를 따릅니다. 각 영역 문서는 다른 영역 문서 없이 쓸 수 있게 독립적으로 작성했습니다.

## 확인 항목

- **불필요한 연산:** 루프 안의 반복 계산·정규식 컴파일·직렬화, O(n²) 탐색(배열 `includes`·`find`를 루프 안에서), 렌더마다 반복되는 대량 연산
- **DB 조회 패턴:** N+1 쿼리, 인덱스가 없는 조건·정렬, `SELECT *`로 큰 컬럼 로드, 페이지네이션 없는 전체 조회, 루프 안의 개별 INSERT·UPDATE
- **네트워크·API 호출:** 루프 안의 원격 호출(배치 API가 있는데 미사용), 병렬 가능한 호출의 직렬 `await`, 요청 워터폴
- **캐시:** 캐시 무효화 누락(→ `correctness`일 수 있음), 상한 없는 메모리 캐시, 캐시 키가 너무 넓거나 좁음
- **메모리:** 대용량 파일·결과 집합을 전부 메모리에 적재(스트리밍 미사용), 이벤트 리스너·타이머 누수, 전역 컬렉션 무한 증가
- **렌더링(프런트엔드):** 불필요한 리렌더, 가상화 없는 대형 리스트, 무거운 의존성의 번들 유입, 레이아웃 스래싱
- **동기 블로킹:** 이벤트 루프·요청 스레드에서 동기 I/O, 큰 JSON 동기 파싱

## 판단 기준

- 핫 패스(요청마다, 렌더마다, 대량 데이터 처리)인지 근거를 확인합니다. 한 번만 실행되는 초기화 코드의 미세 최적화는 보고하지 않습니다.
- 데이터 크기 가정(사용자 수, 행 수)을 근거에 적습니다. 확인하지 못하면 확신도를 낮춥니다.

## 심각도 예시

판단 기준을 맞추기 위한 예시입니다. 실제 심각도는 `severity.md` 1.1절의 요소로 조정합니다.

| 심각도 | 예시 |
|---|---|
| Critical | 모든 요청에서 전체 테이블을 메모리로 읽어 운영 트래픽에서 OOM으로 서비스 중단 |
| Critical | 무한 재시도 루프가 외부 API를 폭주시켜 계정 차단·전체 기능 정지 |
| High | 주문 목록 API에서 주문마다 고객·상품을 개별 조회하는 N+1로 페이지당 수백 쿼리 |
| High | 새 검색 조건에 인덱스가 없어 대형 테이블 전체 스캔이 매 요청 발생 |
| Medium | 렌더마다 수천 건을 정렬·필터해 입력 지연 발생 |
| Medium | 가상화 없이 수천 행 리스트를 렌더 |
| Medium | 서로 독립인 API 호출 3개를 직렬 `await` |
| Low | 한 번만 실행되는 초기화 코드의 비효율 |
| Low | 아이콘 라이브러리 전체 import로 번들이 약간 증가 |
