# 보고서: 발견 항목 헤더와 본문

리뷰할 때 항상 읽습니다. **헤더 문법(1~3절)은 품질 채점 스크립트(`tests/score-quality.sh`)와 공유하는 계약**이므로 글자 하나까지 그대로 지킵니다. 경로에 제어문자, `\`, `"`, ` · `, ` → `가 있으면 `path-quoting.md`도 읽습니다.

## 1. 헤더 형식

    [S-NN] <심각도> · 확신도 <확신도> · <영역 slug> · <위치>

| 요소 | 허용 값 |
|---|---|
| `NN` | 10진수 두 자리 이상, `01`부터 순서대로(`01` … `99`, `100` …) |
| 심각도 | `Critical` \| `High` \| `Medium` \| `Low` (영어 그대로, 첫 글자만 대문자) |
| 확신도 | `High` \| `Medium` \| `Low` |
| 영역 slug | `security` \| `correctness` \| `ops` \| `architecture` \| `performance` \| `tests` \| `readability` \| `style` (소문자. `a11y`는 slug가 아니며 접근성 문제는 `correctness`) |
| 위치 | 3절 |

- 헤더는 줄 맨 앞(들여쓰기 없음)에서 `[S-`로 시작합니다. 앞에 `-`, `*`, `#`, `**`, 백틱 같은 장식을 붙이지 않고, 헤더 줄 끝에 다른 말을 덧붙이지 않습니다. 장식을 붙인 줄은 헤더로 인식되지 않아 그 발견이 누락됩니다.
- `[S-`로 시작하는 줄은 발견 항목 헤더에만 씁니다. 문법에 맞지 않는 `[S-` 줄은 채점에서 **출력 형식 오류**로 처리되고, 그 실행 전체가 실패로 판정됩니다.

## 2. 파싱 규칙

1. 줄이 `[S-`로 시작하면 헤더 후보입니다. `[S-` 다음에 10진수 두 자리 이상과 `] `가 와야 합니다.
2. 나머지를 앞에서부터 ` · ` 구분자 **3개만** 분리합니다: `<심각도>`, `확신도 <확신도>`, `<영역 slug>`, 그리고 나머지 **전체**가 `<위치>`입니다. 위치 안에 ` · `가 있어도 더 나누지 않습니다.
3. 위치가 ` (삭제)`로 끝나면 삭제 위치이며, 그 접미어를 떼고 계속합니다.
4. 남은 문자열의 **마지막 `:`** 뒤가 줄 범위, 앞이 경로 부분입니다. 줄 범위는 `L` 또는 `L-L`(10진수, 시작 ≤ 끝)이어야 합니다.
5. 경로 부분이 `"`로 시작하면 C 스타일 따옴표 문자열로 읽어, 이스케이프되지 않은 닫는 `"`까지를 한 경로로 디코딩합니다. 아니면 ` → `가 나오기 전까지(없으면 끝까지)가 경로입니다.
6. 첫 경로 뒤에 ` → `가 있으면 이름 변경이며, 그 뒤가 새 경로입니다(같은 방식으로 따옴표 처리). 이름 변경 항목의 대상 파일은 새 경로입니다.
7. 위 어느 단계라도 맞지 않으면 출력 형식 오류입니다. 예: `[S-1]`(번호 한 자리), `high`(대소문자), 확신도 누락, `a11y`를 slug로 씀, 줄 범위 누락, `:L3`(숫자 아님), ` - ` 구분자, `높음 · 확신도 높음 · 보안`(번역).

## 3. 위치 형식

위치는 저장소 최상위 기준 상대 경로와 줄 범위입니다(`./`, 절대 경로, `a/`·`b/` 접두어를 붙이지 않음).

| 변경 종류 | 형식 | 줄 번호 기준 | 예 |
|---|---|---|---|
| 신규·수정 | `경로:L` 또는 `경로:L-L` | 변경 후(리뷰 스냅샷) 파일 | `src/app.ts:42`, `src/app.ts:42-48` |
| 삭제 | `경로:L-L (삭제)` (한 줄이면 `12-12`) | 변경 전 파일 | `src/legacy/auth.ts:12-30 (삭제)` |
| 이름 변경 | `이전경로 → 새경로:L-L` (한 줄이면 `5-5`) | 새 파일 | `src/old.ts → src/new.ts:5-9` |

- 줄을 특정할 수 없는 파일 단위 문제(예: Dockerfile에 `USER` 없음, manifest와 lockfile 불일치)는 가장 관련 있는 줄을 가리킵니다(예: `FROM` 줄, manifest의 해당 의존성 줄). 그래도 없으면 `:1`을 씁니다.
- 줄 번호는 리뷰 스냅샷(작업 트리, index, 해당 커밋)의 파일 기준입니다. `config/a:b.yaml:7`처럼 경로에 `:`가 있어도 마지막 `:` 뒤가 줄 범위입니다.
- 번호는 `numbered_diff_file`의 번호 열에서 가져옵니다. 신규·수정·이름 변경 위치는 `<변경 후 줄>`, 삭제 위치는 `<변경 전 줄>`입니다. 예를 들어 번호 diff의 82번째 줄이 `           25 | +router.get(...)`이면 위치는 `:25`입니다.
- diff 밖의 줄(관련 코드, 기존 코드 근거)은 리뷰 스냅샷 파일을 직접 읽어 번호를 확인합니다.
- 근거 코드를 인용할 때는 번호 열과 `| `, diff 기호(`+`·`-`·공백)를 빼고 코드만 씁니다.
- `  같은 원인: <위치>` 줄도 같은 위치 문법을 쓰고, 위치가 여러 개면 위치마다 한 줄씩 반복합니다.

## 4. 본문 (standard·deep)

헤더 다음 줄부터 두 칸 들여쓰기로 씁니다. quick은 `quick.md`의 축약형을 씁니다.

| 줄 | 내용 |
|---|---|
| `문제:` | 무엇이 잘못됐는지 한 문장. 확신도 Low면 끝에 `(미검증)` |
| `조건:` | 문제가 발생하는 입력·상태·환경 |
| `영향:` | 누가, 무엇을, 얼마나 잃는지 |
| `근거:` | 위치와 코드 5줄 이내 인용(다음 줄부터 네 칸 이상 들여쓰기). 관련 코드·의도 원문 인용 가능. 같은 스냅샷에서 확인하지 못한 맥락이면 그 사실 |
| `수정:` | 5줄 이내 diff 또는 한 문장 |
| `같은 원인:` | 있을 때만. 위치마다 한 줄 |

- 근본 원인이 같은 문제는 한 항목으로 묶습니다. 코드를 직접 고치지 않고 수정은 제안만 합니다.
- focus 밖 영역에서 우연히 확인한 Critical은 보고하되 `문제:` 끝에 `(focus 밖 부수 발견)`을 붙이고, 영역별 결과의 그 영역은 "미검토(focus 제외)"로 둡니다.

## 5. 정렬, 번호, 하위 섹션

- 정렬: 심각도(Critical → High → Medium → Low) → 확신도(High → Medium → Low) → 파일 경로(디코딩한 경로의 사전순) → 시작 줄.
- 보고 규칙(`../review/severity.md` 3절), `--min-severity`, `--max-findings`를 적용한 **뒤에** 번호를 `S-01`부터 매깁니다. 본문 항목을 먼저 매기고, 이어서 "검토 권장" 항목을 같은 정렬 규칙으로 이어 매깁니다.
- `--max-findings`를 넘으면 심각도 → 확신도 순으로 자르고, 목록 끝에 `그 외 N건(주로 <가장 많은 심각도>)` 한 줄을 적습니다. Critical은 상한을 넘어도 모두 보고합니다.
- **검토 권장:** strict에서 확신도 Low 항목만 `### 검토 권장 (strict, 확신도 Low)` 아래에 둡니다. 헤더 문법은 같고 번호는 본문에 이어 매깁니다. balanced에는 이 섹션이 없습니다.
- **범위 밖 관찰:** 변경과 무관한 기존 문제 중 심각도 High 이상만, 최대 3건을 `### 범위 밖 관찰` 아래에 적습니다. 번호는 `O-NN`입니다: `[O-01] High · 확신도 Medium · security · src/legacy/login.ts:20-25`. 위치 문법은 같고 본문은 `문제:`와 `근거:` 두 줄입니다. `[S-`로 시작하지 않으므로 채점과 "발견" 개수에 들어가지 않습니다.
- 항목이 없는 하위 섹션(`### 검토 권장`, `### 범위 밖 관찰`)은 제목도 쓰지 않습니다.
